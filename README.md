# Bullet in Flight

A point-mass exterior ballistics calculator. Enter a load and a sight setup; get a
range table (velocity, energy, height above/below the line of sight) and a chart of
the arc from the muzzle out to a chosen distance. Also does wind deflection, unit
switching, a saved-load library, a compare view, an 855-round commercial ammo
catalog, and a "vitals window" / optimal-zero tool — see **Features** below.

Live: https://clyel.github.io/bullet-in-flight/ (public GitHub Pages, auto-deploys
on every push to `main` via `.github/workflows/deploy.yml`, which runs `npm test`
first — a broken change won't go live).

## Running it

```bash
npm install
npm run dev     # http://localhost:5173
npm test        # solver checks against reference fixtures
```

## How the physics works

**Point-mass model.** The bullet is treated as a particle with two forces on it:
gravity and aerodynamic drag. Position and velocity are stepped forward in fixed
0.25 ms increments (forward Euler). Spin, yaw, and lift are ignored — those matter
for extreme long range, not for the ranges this tool covers.

**Drag.** Drag deceleration is

```
a = 0.0877382 * rho * v^2 * Cd(M) / BC
```

where `rho` is air density in slug/ft^3, `v` is speed in ft/s, `Cd(M)` is read from
the standard drag table by linear interpolation on Mach number, and `BC` is the
ballistic coefficient in lb/in^2. The leading constant is `0.5 * (pi/576) * 32.174`,
which folds in the circular reference area, the in^2-to-ft^2 conversion, and
pounds-mass to slugs.

**Drag tables.** `src/ballistics/dragTables.js` holds the BRL-tabulated G1 (79 points)
and G7 (84 points) Cd-vs-Mach curves. These are generated data — do not hand-edit them.
G1 is the flat-base reference; G7 is the boat-tail reference. A BC published as G1 must
be used with G1, and likewise for G7. Mixing them produces confidently wrong answers.

**Line of sight and zeroing.** The line of sight is the x-axis. The bullet starts one
sight height below it and is launched at an angle found by secant iteration so that the
trajectory crosses zero exactly at the zero range. This is why most loads show two
zeros — a near one on the way up and the nominal one on the way down — and a positive
max ordinate in between.

**Wind.** A constant 3D wind vector, resolved from a speed and a clock-face direction
(12 = headwind, 3 = right cheek, 6 = tailwind, 9 = left cheek). Drag acts on velocity
*relative to the moving air*, not ground velocity — at every step the relative-velocity
vector is what gets Mach-looked-up and decelerated, then that deceleration is applied
to the bullet's ground velocity. With no wind entered, relative velocity equals ground
velocity and this is identical to the pre-wind physics.

**Atmosphere.** Density and speed of sound come from station (absolute) pressure and
temperature. The altitude field only prefills those two values from the ICAO standard
atmosphere; it is never applied on top of a pressure the user entered. Double-counting
altitude is the most common way to get quietly wrong numbers here.

**Vitals window / optimal zero.** Not new trajectory physics — an outer layer on top
of the solver (`src/ballistics/vitalsWindow.js`). `vitalsWindow(path, radius)` scans an
already-integrated path for the single continuous span the trajectory stays within
+/-radius of the line of sight, ending at whichever boundary (top or bottom) it
violates first. `optimalSightIn(base, radius)` finds the zero range that maximizes
that span — apex height isn't monotonic in zero range across the full practical range
(very short zeros need steep angles that blow the apex sky-high before the familiar
"longer zero -> higher apex" regime kicks in), so it locates the valley bottom first
(ternary search), then bisects only the increasing branch beyond it.

## Accuracy

`npm test` checks the solver against fixtures generated by `py-ballisticcalc`, an
independent RK4 implementation, across cartridges with and without wind, out to 1000
yards. Current agreement:

| Check | Worst deviation |
| --- | --- |
| Zero launch angle | 0.0001 deg |
| Velocity | 1.0 fps |
| Energy | 0.8 ft-lb |
| Height | 0.15 in |
| Windage | 0.06 in |
| Time of flight | 0.0005 s |

Regenerate fixtures with `test/fixtures/generate.py` if the reference solver is
updated. The vitals-window/optimal-zero layer isn't new trajectory physics, so it
doesn't need independent fixtures — instead `test/solver.test.mjs` checks it against
itself (the found zero's apex sits at the target radius, and neighboring zeros give a
smaller window, never a wider one).

## Features

- **Wind deflection**, MOA/MIL correction columns (off by default), Imperial/Metric
  unit switching (canonical-imperial internally, converted only at the edges).
- **Saved Datasets** — name and save a full load snapshot (ammo + rifle + conditions)
  to `localStorage`; persists across sessions on the same browser/device, does not
  sync across devices.
- **Compare tab** — overlay several saved loads on one chart plus a single-distance
  table, with a "Compare at" field that scales the chart to match.
- **Commercial ammo catalog** — 855 entries across Remington, Weatherby, Hornady, and
  Federal (`src/data/commercialAmmo.js`), picked via a cascading Caliber ->
  Manufacturer -> Load selector (`src/components/CommercialLoadPicker.jsx`). BC is
  published where the manufacturer states one; where they don't (Hornady entirely,
  most of Federal), it's back-calculated by bisection against this app's own solver
  from the manufacturer's own published velocity table — see the header comment in
  `commercialAmmo.js` and `scripts/deriveBC.mjs` for the method and validation.
- **Vitals Zero / vitals window / Optimal Zero tab** — a per-load, user-set vital-zone
  radius drives reference lines on the charts, a live "how far does this trajectory
  stay in the vitals band at my current zero" readout, an on-demand "what zero
  maximizes that" toggle, and a dedicated tab for comparing the optimal zero across as
  many catalog rounds or saved datasets as you want against one shared rig.

## Layout

```
src/
  ballistics/
    dragTables.js       generated G1/G7 Cd-vs-Mach data
    atmosphere.js        air density, speed of sound, standard atmosphere
    solver.js             integration, zeroing, sampling, Mach/sight-line crossings
    vitalsWindow.js    vitals-window scan + optimal-zero search (built on solver.js)
    angular.js             inches -> MOA/MIL
  components/            presentational React only, no physics
  data/
    commercialAmmo.js  855-entry commercial ammo catalog
  storage/
    savedLoads.js         localStorage get/save/delete
  App.jsx, Calculator.jsx, Compare.jsx, OptimalZero.jsx    the three tabs
  UnitsContext.jsx, units.js, solveFromForm.js               cross-cutting glue
scripts/
  deriveBC.mjs, fit*.mjs, *_raw.py    BC back-calculation + catalog transcription
test/
  solver.test.mjs    fixture comparison + vitals-window self-consistency checks
  fixtures/            reference trajectories + generator
.github/workflows/
  deploy.yml    build, test, deploy to GitHub Pages on push to main
```

Physics lives in `src/ballistics/` and knows nothing about React. Components take a
solved trajectory and render it. Keep that boundary — it is what makes the solver
testable.

## Not modeled yet

Spin drift, Coriolis, aerodynamic jump, and powder temperature sensitivity. Transonic
(Mach 1.2 down to 1.0) is shaded on the chart and tinted in the table because that is
where G1/G7 standard curves diverge most from a real bullet's measured drag; treat
predictions there as soft.
